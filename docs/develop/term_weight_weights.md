# `term_weight.Dealer.weights()` 详解

本文专门讲解 [term_weight.py](/E:/py/ragflow/rag/nlp/term_weight.py) 里的 `Dealer.weights()`。

目标不是只解释“它会返回一个权重列表”，而是把下面这些问题讲透：

- 它到底想解决什么问题
- 输入会经过哪些预处理
- `ner`、`postag`、`freq`、`df`、`idf` 分别在干什么
- 最终权重公式是什么
- 为什么要这样设计
- 在真实查询里大概会算出怎样的结果

---

## 1. 它在整个检索链路里的作用

`weights()` 的职责可以概括成一句话：

**把一组 token 转成“重要性不同”的加权 token。**

RAGFlow 后面的全文检索构造，不是把所有词一视同仁地丢给搜索引擎，而是会让更关键的词拥有更高的 boost。

比如：

- `RAGFlow`
- `知识库`
- `向量检索`

这类词通常比：

- `请问`
- `怎么`
- `的`
- `a`
- `is`

更值得影响召回和排序。

所以 `weights()` 做的事，本质上是：

1. 看这个 token 稀不稀有
2. 看它是不是实体词
3. 看它是什么词性
4. 把这些因素组合成一个分数
5. 再把分数归一化，输出给上层使用

在 [query.py](/E:/py/ragflow/rag/nlp/query.py) 里，`question()` 会调用它，把结果拼进最终查询表达式。

---

## 2. 函数入口

函数定义：

```python
def weights(self, tks, preprocess=True):
```

参数含义：

- `tks`
  - 输入 token 列表
  - 当 `preprocess=False` 时，认为这里已经是切好的 token
  - 当 `preprocess=True` 时，里面也可能是句子片段，函数内部会继续做预处理
- `preprocess`
  - 是否先做 `pretoken()` 和 `token_merge()`

返回值：

```python
[(token1, weight1), (token2, weight2), ...]
```

而且这些 `weight` 是归一化后的，相加大致等于 `1`。

---

## 3. 先看完整思路

`weights()` 的整体逻辑可以压缩成下面这条链：

```text
原始输入
-> 预切分 pretoken()
-> 合并 token_merge()
-> 对每个 token 计算：
   稀有度(idf1, idf2) × 实体权重(ner) × 词性权重(postag)
-> 得到原始分数
-> 归一化
-> 输出
```

其中最核心的公式是：

```text
raw_weight(t)
= (0.3 * idf(freq(t)) + 0.7 * idf(df(t))) * ner(t) * postag(t)
```

最后再做：

```text
final_weight(t) = raw_weight(t) / sum(raw_weight(all_tokens))
```

这里有两个关键点：

- `idf(freq(t))`
  - 更像“词本身常不常见”
- `idf(df(t))`
  - 更像“它在多少文档里都出现过”

代码把 `df` 那一路的占比设得更高，是因为文档级区分能力通常比单纯词频更稳。

---

## 4. preprocess=True 时，前面发生了什么

当 `preprocess=True`，函数不会直接拿输入逐个打分，而是先做：

```python
tt = self.token_merge(self.pretoken(tk, True))
```

也就是说，每个输入项会先经历两步。

### 4.1 `pretoken()`

`pretoken()` 负责做比较粗的切分和清洗，目标是得到一批“基本可用”的候选 token。

它会做这些事情：

- 调 `rag_tokenizer.tokenize(txt)` 做基础分词
- 去掉停用词
- 过滤一些纯符号噪音
- 根据参数控制是否保留数字类 token

例如：

```text
输入：请问 RAGFlow 的向量检索怎么做
pretoken 后可能得到：
["ragflow", "向量", "检索", "做"]
```

这里像 `请问`、`的`、`怎么` 这类低信息词通常就会被扔掉。

### 4.2 `token_merge()`

`token_merge()` 负责把一些过碎的 token 合并回更像“检索词”的形态。

为什么要有这一步：

- 分词器有时会把短英文、短数字、单字切得过碎
- 过碎之后权重会被摊薄
- 查询构造时也容易失去短语语义

例如，输入 token 可能像这样：

```text
["r", "a", "g", "检索"]
```

合并后可能更接近：

```text
["r a g", "检索"]
```

再比如：

```text
["多", "工位", "管理"]
```

会尽量避免把一个本应连着看的概念切得太散。

所以：

- `pretoken()` 偏“切开和过滤”
- `token_merge()` 偏“把切得太碎的再拼回去”

## 5. 四个局部评分器分别在做什么

`weights()` 里面嵌了四个重要函数：

- `ner(t)`
- `postag(t)`
- `freq(t)`
- `df(t)`

它们分别从不同角度判断 token 是否重要。

### 5.1 `ner(t)`：实体类型权重

代码逻辑可以简化成这样：

```python
if token 是纯数字类:
    return 2
if token 是很短的英文:
    return 0.01
if token 不在命名实体词典里:
    return 1
否则按实体类型映射表返回权重
```

映射表大致是：

```python
{
    "toxic": 2,
    "func": 1,
    "corp": 3,
    "loca": 3,
    "sch": 3,
    "stock": 3,
    "firstnm": 1
}
```

这代表：

- 公司、地点、学校、股票代码这类实体更重要
- 普通功能性实体保持默认
- 很短英文片段极度降权

为什么短英文要降到 `0.01` 这么低？

因为这类 token 很容易是：

- `a`
- `an`
- `to`
- `of`
- `x`

或者分词残片。  
如果不给它们强力降权，这些噪音在英文查询里很容易干扰排序。

### 5.2 `postag(t)`：词性权重

这里调用了：

```python
t = rag_tokenizer.tag(t)
```

然后按词性给不同权重。

规则大致是：

- 代词 / 连词 / 副词：`0.3`
- 地名 / 机构名：`3`
- 普通名词：`2`
- 数字类：`2`
- 其他：`1`

这一步的核心思路是：

- 检索通常更关心“主题词”
- 名词和实体通常最像主题词
- 代词、连词、副词更像语法胶水

比如下面两个词：

- `北京`
- `怎么`

即使词频相近，`北京` 对检索也明显更有价值，所以会被额外抬高。

### 5.3 `freq(t)`：词频估计

`freq(t)` 想回答的问题是：

**这个词在通用语料里常不常见？**

注意，这里不是直接拿真实出现次数去算最终权重，而是后面会通过 `idf()` 转成“稀有度”。

它的大致逻辑是：

1. 如果像编号/数字串，直接给固定值 `3`
2. 否则从 `rag_tokenizer.freq(t)` 里查词频
3. 如果查不到，但它是英文术语，则给一个经验值 `300`
4. 如果还是查不到，而且 token 很长，就把它细切后用子词频率反推
5. 最后设下限 `10`

这里有几个非常关键的设计。

#### 5.3.1 为什么数字类直接给固定频率

比如：

- `2024`
- `3.5`
- `A-102`

这类 token 在通用词典里常常不稳定，甚至查不到。  
但在业务检索里它们往往极重要，所以不能简单按“未知词”处理。

#### 5.3.2 为什么英文未知词给 `300`

比如：

- `ragflow`
- `langgraph`
- `milvus`

这类技术名词在通用中文词典里很可能不存在。  
如果把它们当成频率 `0`，后面的 `idf` 会把它们放得过高，数值容易失真；如果当成完全不重要也不对。

所以这里选了一个折中经验值：

- 承认它不常见
- 但不把它当成“极端稀有神词”

#### 5.3.3 为什么长词要拆开再估计

比如：

```text
向量数据库
```

如果词典里没有整词频率，不能立刻判它是坏词。  
它可能只是一个复合词，于是代码会细切成类似：

```text
["向量", "数据库"]
```

然后取这些子词里更保守的频率，再除以 `6`。

这相当于在说：

“这个长词应该比常见子词更稀一些，但我也不敢把它当成极稀有词，所以只给一个收缩后的估值。”

### 5.4 `df(t)`：文档频次估计

`df(t)` 和 `freq(t)` 很像，但关注点不同。

它想回答的是：

**这个词会不会在大量文档里都出现？**

比如：

- `系统`
- `功能`
- `问题`

可能词频不算离谱，但几乎什么文档里都能看到，它们的区分度就没那么强。

而：

- `RAGFlow`
- `Infinity`
- `Milvus`

可能只在一小批文档里出现，文档区分能力就更强。

逻辑大致是：

1. 数字类给固定值 `5`
2. 如果在 `self.df` 词典里，取 `self.df[t] + 3`
3. 英文未知词给经验值 `300`
4. 长复合词则拆成子词推测
5. 默认返回 `3`

这里和 `freq()` 的区别在于：

- `freq()` 更偏词在语言层面常不常见
- `df()` 更偏词在文档集合里分布广不广

---

## 6. `idf()` 在做什么

代码是：

```python
def idf(s, N):
    return math.log10(10 + ((N - s + 0.5) / (s + 0.5)))
```

它是一个做了平滑的 IDF。

核心规律：

- `s` 越小，说明词越稀有，`idf` 越大
- `s` 越大，说明词越常见，`idf` 越小

这里：

- `s` 可以是词频估计，也可以是文档频次估计
- `N` 是一个经验性的总量

代码里用的是：

- `freq` 那一路：`N = 10000000`
- `df` 那一路：`N = 1000000000`

为什么不直接用真实语料规模？

因为这里更像是一套稳定的启发式打分，不要求严格概率意义，只要求：

- 稀有词比常见词分数更高
- 不同量级下数值别炸掉
- 整体趋势稳定

前面的 `10` 和 `0.5` 都是平滑项，用来避免极端值太夸张。

---

## 7. 最终总公式

对于每个 token `t`，原始分数是：

```text
raw(t) = (0.3 * idf(freq(t)) + 0.7 * idf(df(t))) * ner(t) * postag(t)
```

再统一归一化：

```text
final(t) = raw(t) / Σ raw(all_tokens)
```

这说明它不是单一 TF-IDF，而是：

**启发式 IDF + 实体加权 + 词性加权 的混合评分。**

---

## 8. 为什么 `df` 权重比 `freq` 更大

代码里这句很关键：

```python
wts = (0.3 * idf1 + 0.7 * idf2) * np.array([ner(t) * postag(t) for t in tt])
```

也就是：

- `idf1 = idf(freq(t))`
- `idf2 = idf(df(t))`

而且是：

```text
0.3 * idf1 + 0.7 * idf2
```

这背后的直觉是：

- 词本身常不常见，重要
- 但它在文档集合中是不是“到处都有”，对检索区分度更关键

举个对比：

### 例子 1：`系统`

- 词频可能不低
- 文档频次也很高

所以它大概率是常见背景词，不应太强。

### 例子 2：`RAGFlow`

- 词频可能不高
- 文档频次通常也不高

所以它更像真正区分某一批文档的关键术语。

因此把 `df` 这一路设得更重，更符合搜索系统的目标。

## 9. 完整例子一：中文技术问题

假设输入问题是：

```text
RAGFlow 知识库向量检索怎么做
```

### 9.1 预处理后的 token

先忽略问句壳子，`pretoken()` + `token_merge()` 后，可能得到：

```text
["ragflow", "知识库", "向量", "检索"]
```

下面我们用一组“便于理解的假设值”来说明，不代表线上真实词典数值完全相同。

| token | freq(t) | df(t) | ner(t) | postag(t) |
|---|---:|---:|---:|---:|
| ragflow | 300 | 300 | 1 | 1 |
| 知识库 | 120 | 80 | 1 | 2 |
| 向量 | 200 | 150 | 1 | 2 |
| 检索 | 180 | 140 | 1 | 2 |

### 9.2 先看稀有度直觉

通常来说：

- `ragflow` 比 `向量`、`检索` 更稀有
- `知识库`、`向量`、`检索` 是名词，所以会被 `postag=2` 抬高

这就形成一个很有意思的平衡：

- `ragflow` 稀有，但词性加成没那么高
- `知识库/向量/检索` 稍常见，但属于核心名词

### 9.3 假设得到的原始分数

假设最后算出来：

| token | raw(t) |
|---|---:|
| ragflow | 4.2 |
| 知识库 | 6.0 |
| 向量 | 5.1 |
| 检索 | 5.4 |

总和：

```text
S = 4.2 + 6.0 + 5.1 + 5.4 = 20.7
```

归一化后：

| token | final(t) |
|---|---:|
| ragflow | 0.203 |
| 知识库 | 0.290 |
| 向量 | 0.246 |
| 检索 | 0.261 |

这意味着：

- `知识库`
- `检索`
- `向量`

会比 `ragflow` 略强一些地影响最终查询。

这其实很合理，因为这个问题问的是“知识库向量检索怎么做”，`ragflow` 是场景名，后面几个词更像真正的主题核心。

## 10. 完整例子二：带数字和型号

假设输入是：

```text
A100 显卡 80GB 参数
```

预处理后可能得到：

```text
["a100", "显卡", "80gb", "参数"]
```

这里数字/型号类 token 会比较占优势，因为：

- 型号本身区分度很强
- 数字类 token 在 `ner()` 和 `freq()/df()` 里都有特别照顾

假设：

| token | 解释 |
|---|---|
| a100 | 型号词，非常关键 |
| 显卡 | 主题名词，很关键 |
| 80gb | 容量规格，很关键 |
| 参数 | 泛词，信息量相对弱 |

可能出现的结果趋势是：

```text
显卡 ≈ a100 ≈ 80gb > 参数
```

为什么 `参数` 往往最弱？

因为它虽然是名词，但太泛了，很多文档都可能包含它，`df` 往往不会低。

## 11. 完整例子三：英文短词为什么会被强烈降权

假设输入是：

```text
what is a rag workflow
```

经过上游清洗后，可能剩下：

```text
["rag", "workflow", "a"]
```

如果不专门压低短英文：

- `a`
- `is`
- `to`
- `of`

这类词会频繁混进英文查询，污染排序。

而当前逻辑里：

```python
if short_letter_pattern.match(t):
    return 0.01
```

于是像 `a` 这种 token 即便保留下来，也几乎不会影响最终权重。

这一步对英文查询特别重要。

## 12. `preprocess=False` 时和 `True` 有什么区别

### 12.1 `preprocess=False`

表示调用方已经切好 token 了。

例如：

```python
tks = ["知识库", "检索", "向量数据库"]
w = dealer.weights(tks, preprocess=False)
```

这时函数会：

- 直接对这 3 个 token 计算分数
- 不再调用 `pretoken()` 和 `token_merge()`

适合场景：

- 上层已经做过分词
- 不想被再次切分

### 12.2 `preprocess=True`

表示输入项可能还偏“原始文本片段”。

例如：

```python
tks = ["RAGFlow 知识库向量检索"]
w = dealer.weights(tks, preprocess=True)
```

这时函数会先拆开再算，更适合自然语言输入。

## 13. 它不是标准 TF-IDF，而是“工程化搜索权重”

如果只从学术术语上看，很多人会以为它是 TF-IDF。

其实不完全是。

它更像一套面向检索工程的混合打分器：

- 有 IDF 思想
- 但没有严格按标准 TF 走
- 混入了实体类型知识
- 混入了词性知识
- 对英文术语、数字串、长复合词做了大量兜底

所以它的目标不是“严格还原某篇论文公式”，而是：

**在真实混合语料里，尽可能稳定地把重要词抬出来。**

---

## 14. 这种设计的优点

### 14.1 对技术术语比较友好

像：

- `RAGFlow`
- `LangGraph`
- `Milvus`
- `A100`

即便不在通用中文词典里，也不会被简单判成垃圾词。

### 14.2 对中文主题词有加强

名词、地名、机构名等会被显式升权，更贴合检索需求。

### 14.3 对噪音词有抑制

短英文残片、代词、连词、副词，都会被明显降权。

### 14.4 对未知复合词有兜底

查不到整词时，不会立刻放弃，而是继续细粒度拆分估算。

---

## 15. 它的局限

### 15.1 权重是启发式的

里面很多数字是经验参数，不是自动学习出来的：

- `0.3 / 0.7`
- `0.01`
- `2`
- `3`
- `/ 6`

所以它更依赖经验，而不是严格数据拟合。

### 15.2 依赖词典质量

如果：

- `self.ne`
- `self.df`
- `rag_tokenizer.freq()`
- `rag_tokenizer.tag()`

这些底层资源质量一般，权重质量也会受影响。

### 15.3 无法理解更深层语义

它能判断“这个词重要不重要”，但不能判断：

- 句子真正意图
- 多义词上下文差异
- 跨词组合语义

这也是为什么后面系统还需要：

- 向量检索
- rerank
- hybrid score

---

## 16. 可以把它理解成什么

如果一定要给它一个最贴切的名字，可以把它理解成：

**一个为查询构造服务的“关键词显著性打分器”。**

不是纯分词器。

不是纯 TF-IDF。

不是语义模型。

而是站在工程检索角度，综合考虑：

- 稀有度
- 词性
- 实体类型
- 英文/数字/复合词兜底

最后给出一组“谁更该影响召回”的相对权重。

---

## 17. 一句话总结

`Dealer.weights()` 的核心思想是：

**用“稀有度 + 实体类型 + 词性”三类信号，给 token 做一个工程化的重要性排序，再把结果归一化，供后续检索查询拼装使用。**

如果你后面继续看 [query.py](/E:/py/ragflow/rag/nlp/query.py) 的 `question()`，就会发现这些权重会直接决定：

- 哪些词 boost 更高
- 哪些词值得扩同义词
- 哪些词更能影响全文召回和排序
