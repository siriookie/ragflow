# 中英文边界补空格优化

## 背景

在 RAG 检索场景里，用户很常输入中英文混写内容，例如：

- `RAG检索`
- `检索RAG`
- `RAGFlow2向量检索`
- `知识库FAQ`

这类文本对人来说很容易理解，但对后续分词、关键词加权和全文检索构造并不友好。  
如果中英文直接连在一起，没有明显边界，分词器很容易把它们黏成一个整体 token，导致：

- 英文术语无法被单独识别
- 中文词无法按预期参与检索
- 同义词扩展和权重计算失真
- 查询侧和索引侧 token 边界不一致，增加漏召回概率

为了解决这个问题，RAGFlow 在查询预处理阶段增加了一个轻量优化：**在中英文相邻边界自动补空格**。

## 代码位置

函数位于：

[`common/query_base.py`](/E:/py/ragflow/common/query_base.py)

```python
@staticmethod
def add_space_between_eng_zh(txt):
    txt = re.sub(r'([A-Za-z]+[0-9]+)([\u4e00-\u9fa5]+)', r'\1 \2', txt)
    txt = re.sub(r'([A-Za-z])([\u4e00-\u9fa5]+)', r'\1 \2', txt)
    txt = re.sub(r'([\u4e00-\u9fa5]+)([A-Za-z]+[0-9]+)', r'\1 \2', txt)
    txt = re.sub(r'([\u4e00-\u9fa5]+)([A-Za-z])', r'\1 \2', txt)
    return txt
```

调用入口之一在：

[`rag/nlp/query.py`](/E:/py/ragflow/rag/nlp/query.py)

## 这个优化在做什么

它不是做复杂分词，也不是做语义改写，而是一个更前置、更便宜的文本规范化步骤：

- 当检测到“英文后面紧跟中文”时，在中间插入空格
- 当检测到“中文后面紧跟英文”时，在中间插入空格
- 同时覆盖“英文+数字”和“纯英文”两种常见技术术语形态

处理前后示例：

| 原始文本 | 处理后 |
|---|---|
| `RAG检索` | `RAG 检索` |
| `检索RAG` | `检索 RAG` |
| `RAGFlow2向量数据库` | `RAGFlow2 向量数据库` |
| `知识库FAQ` | `知识库 FAQ` |

## 为什么要这么做

### 1. 让 token 边界更清晰

很多 tokenizer 在处理中英混写时，如果中间没有分隔符，会把整段内容当作一个不稳定的混合 token。  
补空格之后：

- 英文术语可以作为英文词被单独识别
- 中文词组可以继续按中文逻辑处理
- 后续的 `tokenize()`、`fine_grained_tokenize()` 会更稳定

### 2. 提高查询和索引的一致性

RAG 的召回效果很依赖“查询侧 token”和“索引侧 token”是否一致。  
如果查询输入是 `RAG检索`，而索引里实际更接近 `RAG 检索` 或 `rag 检索`，那就可能出现：

- 查询时英文术语没被单独抽出来
- 索引时英文和中文被分开存储
- 两边 token 形态不一致，导致匹配变弱

这个优化的本质，就是在查询预处理阶段主动把边界补出来，降低这种不一致。

### 3. 改善后续关键词加权

在 [`rag/nlp/query.py`](/E:/py/ragflow/rag/nlp/query.py) 里，查询会进一步经过：

- 分词
- 词权重计算
- 同义词扩展
- query string 拼装

如果中英文混写没有先拆开，像 `RAG检索` 这种输入可能会作为一个整体参与加权。  
这会让：

- `RAG` 这个重要英文术语的权重无法单独体现
- `检索` 这个中文语义词也无法单独体现

补空格后，这两个信号都能被单独保留。

### 4. 这是一个低成本、高收益的优化

这类优化有一个很重要的工程特点：**便宜**。

它只做几次正则替换：

- 不依赖模型
- 不依赖词典
- 不依赖外部服务
- 几乎没有额外延迟

但它对混合语言查询的稳定性提升很明显，尤其适合：

- 技术文档检索
- API 文档问答
- 产品名 / 模型名 / 英文缩写频繁出现的知识库

## 四条规则分别覆盖什么

### 1. 英文或英文+数字 后面跟中文

```python
re.sub(r'([A-Za-z]+[0-9]+)([\u4e00-\u9fa5]+)', r'\1 \2', txt)
```

示例：

- `RAGFlow2检索` -> `RAGFlow2 检索`

### 2. 纯英文 后面跟中文

```python
re.sub(r'([A-Za-z])([\u4e00-\u9fa5]+)', r'\1 \2', txt)
```

示例：

- `RAG检索` -> `RAG 检索`

### 3. 中文 后面跟英文或英文+数字

```python
re.sub(r'([\u4e00-\u9fa5]+)([A-Za-z]+[0-9]+)', r'\1 \2', txt)
```

示例：

- `检索RAGFlow2` -> `检索 RAGFlow2`

### 4. 中文 后面跟纯英文

```python
re.sub(r'([\u4e00-\u9fa5]+)([A-Za-z])', r'\1 \2', txt)
```

示例：

- `检索RAG` -> `检索 RAG`

这四条规则合起来，覆盖了大多数“中英文相邻但中间没有分隔符”的常见输入形式。

## 适用边界

这个优化主要适用于：

- 英文术语、英文缩写、产品名频繁出现的查询
- 中英文混写的技术领域文本
- 查询预处理阶段的轻量规范化

它**不负责**：

- 完整语言识别
- 中文智能分词
- 语义纠错
- 复杂拼写修复

所以应该把它理解为：

**一个为后续检索链路“清边界”的前置规范化步骤**，而不是完整的语言处理方案。

## 在检索链路中的位置

典型流程如下：

1. 用户输入原始问题
2. `add_space_between_eng_zh()` 补齐中英文边界
3. 统一做大小写、全半角、繁简等归一化
4. tokenizer 分词
5. term weight 加权
6. 同义词扩展
7. 构造全文检索表达式 / 混合检索表达式

也就是说，这个优化虽然简单，但位置非常靠前，后续所有 query 构造质量都会受它影响。

## 总结

`add_space_between_eng_zh()` 的价值不在于“做了多复杂的 NLP”，而在于：

- 用极低成本修正中英文混写的边界问题
- 提高查询侧 token 稳定性
- 改善查询侧和索引侧的一致性
- 为后续加权、扩展、全文检索和混合检索打基础

对于技术文档类 RAG 系统，这是一个非常典型、也非常值得保留的工程型优化。
